# プロンプト知識ベース構想

## 目指すもの

このプロジェクトは、タグを大量に並べるだけの辞書で終わらせず、プロンプト系ブログ・解説・作例で見つけた「どう書くと何を表現できるか」を集約し、検索・理解・再利用できる個人向けの知識ベースへ段階的に育てる。

現行のタグ辞書は捨てず、知識ベースの基礎資料・補助機能として維持する。完成を急いで全データを再分類したり、全タグに説明や画像を付けたりしない。

## 設計原則

- まず検索とカテゴリ一覧を中心とする。図やプレビューは補助的な検索手段。
- 小さな変更を積み重ね、既存のタグ検索・選択・プロンプト出力・インポート・ローカル保存を壊さない。
- 事実として確認できた情報、機械的な推定、人が未確認の情報を区別する。
- 分類に迷うデータは無理に決めず「未分類／要確認」に残す。
- 外部のブログ記事を丸ごと複製するのではなく、要点を自分の言葉で整理し、必要な範囲の作例と出典URLを記録する。
- GitHub Pagesで動く静的構成と無料で扱える運用を優先し、サーバー・ログイン・有料APIは必要性が明らかになるまで追加しない。

## 情報の種類

### 1. タグ辞書（現行機能）

タグ名、訳、分類を保持し、検索・選択・プロンプト出力に使う。現在の `data/tags.json` は既存アプリとの互換性があるため、分類基準が安定するまでは単一ファイルを正本として維持する。

将来的に説明・別表記・種別などを拡張する場合も、まずスキーマ案と移行方法を決め、既存データを一度に壊す変更はしない。

### 2. テクニック・作例（将来機能）

ネット上の解説や実験から得た知識を、タグ辞書とは別のレコードとして蓄積する。

1件に持たせる候補：
- 一意なID、タイトル、目的・解決したい問題
- 要約・説明（自分の言葉で記述）
- プロンプト例（そのまま試せる最小例）
- 対象環境・構文（例：使用サービス、モデル、BREAKや重み付けの対応状況）
- 期待される効果、実際に確認した結果、制約・失敗例
- 関連タグ、関連テクニック
- 出典URL、著者・サイト名、参照日
- 検証状態：「未検証」「試行済み」「条件付きで確認」「要再確認」

効果が環境やモデルに依存する場合、一般に保証される書き方として断定しない。

### 3. 作品・固有名詞（必要に応じて追加）

一般タグと作品タイトル・シリーズ・キャラクター・作者名を、文字列の類似だけで同一視しない。例えば一般名詞の `diamond` と、作品タイトル `Diamond Is Unbreakable` は別の概念として扱えるようにする。

候補となる情報は、エンティティ種別、正式名、別表記、親シリーズ、関連タグ。全件に付与するのではなく、曖昧さが実際に問題になるものから整備する。

### 4. 出典・確認記録

出典URLや取得条件が分からない既存データは、推測で補わない。作例については出典URLと確認状態をできるだけ記録する。元記事の全文を保存するのではなく、必要な要点・短い例・自分の検証を中心にする。

## 分類と検索の方針

- 大分類・小分類は、まず現行の分類ルールを整理してから変更する。
- 「分類済み／未分類」「要確認」「タグの種類」は、意味が違うため別の属性として扱う。
- 1つのタグに複数の用途がありそうな場合、すぐにレコードを複製せず、主分類＋補助属性で表現できるか検討する。
- カテゴリをまたいだ検索を維持する。ファイル分割をしても、ユーザーには全体検索を提供する。
- 共通語による枝分かれは、タグ名の表示を短くするための視覚的な補助にすぎない。文字列が共通することは、意味上の親子関係を保証しない。作品名・固有名詞などで誤った階層に見えないか確認し、必要なら例外指定や枝表示の無効化を検討する。

## JSONの分割について

**今は分割しない。** ファイルを分けると編集差分が見やすくなる可能性はあるが、カテゴリ変更時の移動、全体検索時の統合、重複・読み込み漏れの対策が必要になる。

再検討する条件：
- 分類ルールとカテゴリ構造がある程度安定した
- 特定カテゴリだけを独立して編集・レビューする必要が増えた
- データ更新時の差分や競合が、現行の単一ファイル管理で実際に問題になった

分割するときは、カテゴリごとの別々の正本を作るより、タグID・重複排除・統合検索の規則を先に決める。候補ファイルは `tags.json`、`techniques.json`、`examples.json`、`works.json`、`sources.json` など。ただしこれは将来案であり、現在の実装仕様ではない。

## 段階的な進め方

### Phase 0：分類とデータの現状を整理
- 現行カテゴリの意味と分類ルールを記録する。
- 明確な誤分類・誤訳・重複と、判断保留を区別する。
- データの取得元・ライセンス・タグ単位の出典が不明な部分は「不明」のまま記録する。
- JSONの分割や全件の再分類はまだ行わない。

### Phase 1：辞書の検索・一覧を小さく改善
- タグ名の共通語を表示上まとめる機能は、元のタグ名・選択・出力を変えない。
- 共通文字列を意味的な親子関係として扱わない。誤解を招く例は要確認にする。
- 一覧のコンパクト化、検索、カテゴリ一覧の改善を小さなPR単位で行う。

### Phase 2：少数の作例を試験登録
- まず数件のテクニック・作例を手動で記録し、項目が多すぎないか検証する。
- 出典、使用環境、検証状態、プロンプト例を一体で確認できる形にする。
- タグ辞書との関連付けは、既存データを複製せず参照する方式を優先する。

### Phase 3：必要な機能だけ実装
- 作例の検索・目的別フィルター・プロンプトコピーを追加するか検討する。
- 作品・固有名詞の区別や別表記は、実データで困るケースから整備する。
- JSON分割、画像プレビュー、複数カテゴリ対応は、必要性が確認できてから決める。

## いま実装しないもの

- 11,000件すべての手動分類・翻訳校正
- 全タグへの画像プレビュー追加
- 全件に対する作品・キャラクター判定
- 分類ごとのJSON分割
- 自動推定だけでの意味的な親子関係確定
- プロンプトの効果を環境確認なしに保証する説明

## 次に判断すること

1. 現行カテゴリの定義を短いルールとして整理する。
2. 作例1件の記録テンプレートを決める。
3. そのテンプレートで少数の実例を登録して使い勝手を見る。
4. その結果を見てから、アプリ機能やデータ形式を変更する。
