## 1. 目的と優先順位

目的は、画像生成タグを正確に理解し、利用者が服・小物・人物特徴・背景などを探す感覚で選択できる辞典にすること。

優先順位は次のとおり。

1. 未確認・未分類の解消と、既存タグの意味の正確な把握
2. 英文タグと日本語訳の正確性・検索しやすさ
3. タグの意味と用途に合った分類
4. 表現レベルの整備
5. 作品・キャラクター情報、別名、検索性、プロンプト出力の整合
6. 必要な場合に限る分類体系・UI・データ構造の拡張

分類項目や管理ファイルを増やすこと自体は目的にしない。明確なタグを先に処理し、判断が難しいタグは理由を残して要確認にする。未確認を減らすために、根拠のない確定を行ってはならない。

## 2. 正本とファイルの役割

### 唯一の正本

- `data/dictionary-data.json` を辞書データの唯一の正本とする。
- タグ本体、日本語訳、分類、タグ別メタデータ、レビュー状態、分類体系、出力順、タググループ、候補情報、出典情報など、正本が管理する情報はここに集約する。
- 古い分割JSONを新たな正本として復活させない。
- 同じ情報を複数の独立した正本で二重管理しない。

### CSVの役割

- `exports/dictionary-working.csv` は一括確認・編集用の入出力形式であり、正本ではない。
- CSVの変更は、所定のGitHub Actionsで正本JSONへ反映する。
- CSVに含まれない正本側のメタデータやレビュー情報を、インポート時に失ってはならない。
- CSVと正本が食い違う場合は、作業開始時に正本とインポート処理を確認し、CSVを無条件に正しいものとして扱わない。

### その他のファイル

- スクリプト・テスト・ワークフローは、正本の検証や安全な入出力のための実装であり、別の辞書正本ではない。
- 監査レポートは特定時点の調査結果・根拠を残す履歴資料である。現行ルールを定義する場所にはしない。
- Gitのコミット履歴を変更履歴として利用し、独立した変更履歴JSONを新設しない。
- 古いファイルは、内容の移管と参照関係の確認が完了する前に削除しない。

## 3. 正本データの保全

変更時は現在の正本スキーマを先に確認し、既存構造を最大限維持する。

- タグID・英文タグ・配列順は、明確な理由と確認なしに変更しない。
- タグの追加・削除・統合は、翻訳や分類の修正とは別の判断として扱う。
- 既存メタデータ、候補、出典、レビュー根拠を不用意に消さない。
- 既存フィールドの意味を確認せず、新しいフィールド名や保存形式を作らない。
- 分類候補の索引など派生データがある場合は、正本との生成・同期関係を確認し、派生データだけを独立編集しない。
- 古いNSFW関連情報や `nsfwAudit` は、現行の参照先・監査処理・移行先を確認するまで保持する。表現レベルへの移行を理由に機械的に削除・一括変換しない。

## 4. 対象選定と1,000件単位の総合整備

基本単位は1,000件。指定範囲がある場合はその範囲を優先する。

範囲の指定がない場合は、正本のタグ配列を基準に、翻訳・分類・表現レベルのいずれかに未確認または要確認が残るタグを抽出し、元の配列順で最大1,000件を対象にする。すでに確認済みの項目は再作業せず、そのタグで未整備の項目だけを確認する。

- 作業開始時に最新の正本を取得し、対象件数・対象範囲・各レビュー状態を集計する。
- 対象を途中で恣意的に入れ替えない。
- 同じタグを別工程で何度も確認し直すことを避け、一度の対象確認で可能な整備をまとめて行う。
- 内部作業を小分けにしてもよいが、指定された範囲を完了する。
- 1,000件に満たない場合は実際の残件数を報告する。
- 対象外のタグは、明示的な依頼なしに変更しない。
- 作業前後の件数と未解決項目を比較し、処理済みと未処理を区別する。

総合整備では、対象範囲内の英文タグ・日本語訳・分類・表現レベル・作品情報・別名・検索性・プロンプト出力適性をまとめて確認する。

## 5. 英文タグと日本語訳

### 英文タグ

- 英文タグは原則として安定した識別子として維持する。
- 作品名や媒体名を付加する目的で英文タグを書き換えない。
- スペルミス・明白な誤記を直す場合は、正しい表記と影響を確認し、変更理由を記録する。
- 色違い・表記違い・意味の近いタグを安易に統合しない。
- タグの意味を変える改名・削除は、通常の翻訳修正に含めない。

### 日本語訳

- 英文タグの意味と画像生成での用法を確認し、短く自然で検索しやすい日本語にする。
- 機械翻訳調、不自然な直訳、意味の取り違え、修飾関係の誤り、多義語、専門用語、慣用表現を確認する。
- 固有名詞・作品名・キャラクター名・ブランド名・作者名・型番は特に慎重に扱う。
- 正しい訳は無理に変更しない。明確な誤訳や不自然な訳は修正する。
- 英語表記が残っているだけで誤訳と断定しない。正式名称など英語のままが適切なものは原表記を維持する。
- 根拠のない作品名・人物名・意味を推測で補わない。
- 判断できないものは要確認のまま残す。確認した観点だけを `verified` にする。

翻訳の確認状態と分類・表現レベルの確認状態は独立して管理する。一つの項目を確認したことを理由に、他の項目まで確認済みにしない。

## 6. 分類と未分類の解消

分類はタグの実際の意味・用途を基準にし、既存の分類体系と辞典上の検索性を優先する。

- 既存の大分類・中分類・小分類に適切な受け皿があれば、それを利用する。
- 既存分類に無理に押し込まない。必要な場合に限り中分類・小分類を追加する。大分類の追加は慎重に判断する。
- 「その他」や「要確認」を安易な受け皿にしない。意味が明確なタグは適切に分類する。
- 未分類を減らすことを優先し、分類体系の拡張そのものに時間を使いすぎない。
- 自動推定・キーワード一致・既存候補は提案であり、意味上の正しさを保証しない。
- 複合語・固有名詞・文脈依存タグは、語の一部だけで判断しない。
- ポーズ（静的な姿勢）と動作（行為・接触）、人物の特徴とキャラクター固有情報、画風と品質、意味分類と出力先を区別する。
- 色は独立した大分類にしない。色付きタグは対象物・概念を基準に分類する。
- 赤いリボン・青いリボンなど、色違いに実用上の選択価値があるタグは統合・削除しない。
- 色を除いても意味が成立する場合でも、英文タグ自体を機械的に分解・改名しない。色属性や基本概念への関連付けは意味を確認したうえで既存の仕組みに合わせて扱う。
- 肌・髪・目・種族・固有名詞・慣用表現など、色が識別に必要な場合は保持する。
- 作品固有の制服・衣装・装飾・アイテムは一般的な服装・物品と区別し、キャラクター・作品側で扱う。

分類の確認状態は翻訳状態と分離する。判断が難しいタグは、理由を残して要確認とする。

## 7. 作品タイトル・キャラクター・作品固有タグ

作品タイトル単体と、作品に関連するキャラクター・衣装・アイテムを区別する。

### 作品タイトル単体

- 共通の作品タイトル分類の下で、アニメ・ゲーム・漫画・小説・映画など媒体別に分類する。
- 日本語訳は原則として「日本語作品名（媒体名）」の形式にする。
- 公式の日本語表記・媒体を確認できる場合はそれを優先する。
- 複数媒体で展開される作品は、対象タグがどの媒体に由来するかを確認する。
- 媒体や作品名を特定できない場合は推測せず要確認とする。

### キャラクター名・作品固有タグ

- キャラクター名や作品固有の衣装・アイテムは、必要に応じて日本語訳に「タグ名（作品名）」の形式で作品名を付記する。
- 英文タグには作品名を追加しない。
- 一般的な制服・衣服・身体特徴・ポーズには、作品名を付けない。
- 作品固有の制服や装備などは一般的な服装分類に混ぜない。
- 作品名が不明な場合は括弧書きを推測で追加しない。

## 8. 表現レベル（旧NSFW判定）

従来のNSFW二択表示を置き換える辞典内の目安として、表現レベル0〜4を使用する。これは公式な年齢審査ではない。タグ単体の意味・用途を基準とし、実際の生成画像の内容を保証するものではない。

| レベル | 表示名 | 判定の目安 |
|---:|---|---|
| 0 | 一般向け | 通常の服装・日常的な表現。性的要素がほぼない |
| 1 | 軽度の露出 | 水着、肌見せ、軽い露出 |
| 2 | セクシー表現 | 胸元・脚・身体のラインの強調、誘惑的な表現 |
| 3 | 強い性的表現 | 下着、裸に近い露出、性的なポーズ |
| 4 | 成人向け | 性器の露出、明確な性行為 |

判定ルール：

- タグ単体の意味で判定し、組み合わせ後の画像内容を断定しない。
- 性的な意味を持たないタグは原則レベル0とする。
- 通常の衣装・水着・下着タグを一律に成人向けとしない。
- 露出だけを理由に一般的な衣装タグを過剰評価しない。
- 意味や用途が判断できない場合は無理に判定しない。
- 未判定はレベル0ではない。確認できたタグだけに0〜4を設定する。
- 未判定を表すためにタグ本体へ `null` を追加しない。現在のレビュー状態の仕組みを使う。
- 翻訳・分類・表現レベルの確認状態を混同しない。
- 旧NSFWのtrue / false / nullを機械的に0〜4へ変換しない。既存根拠と現在の基準を確認して移行する。
- 旧NSFW情報・監査記録は移行先と参照関係を確認するまで保持する。
- 表現レベルと旧NSFW判定を恒久的な二重管理にしない。移行仕様は現行コード・スキーマ・監査スクリプトを確認して決める。

UIで表示・編集・絞り込みを行う場合は既存画面を最小限変更し、数字だけでなく日本語名称を表示する。未判定を一般向けと誤認させない。

## 9. 別名・検索性・詳細情報

既存の別名・検索キーワード・詳細情報フィールドを優先して利用する。

- 別名は明確な同義語、一般的な表記揺れ、検索されやすい別表現に限る。
- 意味の異なるタグ、色違いタグ、関連するだけのタグを別名として統合しない。
- 重複・不適切な別名は整理してよい。
- 作品名・媒体名・読み方は検索性を高める場合に限り既存フィールドへ追加する。
- 説明・用法・使用例・判定根拠は、補足が実用上必要なタグに限って記録する。
- 実際に確認した出典だけを記録する。架空の出典・根拠を作らない。

## 10. プロンプト出力とネガティブ適性

意味分類とpositive / negativeの出力先は別の概念として扱う。

- タグが何を表すかは意味分類で管理する。
- positive / negativeのどちらへ出力するかは、既存の出力先設定・グループ・出力順の仕組みで管理する。
- 否定的な意味の英単語だからという理由だけでnegativeへ移さない。
- ネガティブ向けタグを意味分類ごと「ネガティブ」に強制移動しない。
- 品質・ネガティブ関連タグは、現在の正本に定義された出力順と例外設定に従う。
- 品質タグの優先順など、確定した出力要件は通常画面・管理画面・コピー・TXT保存で一貫させる。
- `promptOrder` と `tagGroups` を、無関係なタグ修正と一緒に変更しない。

## 11. CSV編集・インポート

CSVは正本を編集するための作業用形式である。現在のCSVヘッダー・スクリプト・GitHub Actionsの実装を確認してから編集する。

現行CSVの列は次の11列を基準とする（実際の正本・CSVヘッダーを作業時に再確認する）。

`index,tag,ja,major,minor,detail,aliases_json,translation_status,expression_level,expression_level_review_status,classification_review_status`

- `index` と `tag` は照合キーのため変更しない。
- 行の並べ替え、追加、削除をしない。
- 列名・列数・全行を維持する。
- `aliases_json` はJSON配列で記録する。空欄は既存値を維持し、別名を明示的に全消去する場合は `[]` を指定する。
- インポートスクリプトは正本JSONと作業CSVを一組として更新し、2ファイル目の置換に失敗した場合は、可能な限り両方を更新前の内容へ戻す。復旧に失敗した場合はバックアップを残してエラーにする。
- `detail` は空欄で既存値を維持し、明示的な削除には `__CLEAR__` を指定する。
- `expression_level` は0〜4、空欄は数値レベルの解除を意味する。
- `translation_status`・`expression_level_review_status`・`classification_review_status` は空欄でstatusのみ解除する。status以外の根拠・メモ等のメタデータは保持する。
- 確認状態はワークフローが許可する値だけを使う。
- CSVに含まれない正本JSONのメタデータ・レビュー記録を保持する。
- 空欄が「変更なし」か「値の削除」かは列ごとのインポート仕様に従う。詳細欄の削除など、明示的なクリア記号が定義されている場合はそれを使う。

標準手順：

1. 最新の正本とCSVを取得し、件数・列・index/tag対応を照合する。
2. 対象行だけ編集し、全行を維持してUTF-8 CSVで保存する。
3. 更新前に `node scripts/import-dictionary-csv.mjs --check` を実行し、正本へ書き込まず全行の照合と変換検証を行う。
4. GitHub上の所定パスへ反映する。
5. 「Import dictionary CSV」ワークフローの成功を確認する。
6. 正本JSONの差分・件数・メタデータ保持を検証する。
7. 失敗時は完了扱いせず、ログと原因を確認する。

## 12. GitHub正本の取得・更新手順

作業は必ずGitHubの最新 `main` を基準にする。アップロード済みファイル、ローカルコピー、過去の集計値を最新の正本として扱わない。

### 取得

1. Git Trees APIまたはContents APIで `data/dictionary-data.json` のBlob SHAを特定する。
2. Blob APIでファイル本体を取得する。
3. Base64の場合は正しくデコードし、JSONとして読み込む。
4. 件数・構造・主要フィールド・取得時点のコミット情報を記録する。
5. 取得に失敗した場合は別のGitHub取得経路を試す。取得できていない状態で編集・集計・更新をしない。
6. 過去の数値を現在の実績として流用しない。

### 更新

1. 対象範囲と変更差分を確認する。
2. JSON構文、タグ件数、ID、英文タグ、配列順、メタデータ、対象外データを検証する。
3. 既存監査スクリプト・関連テストを実行する。
4. 更新直前に正本のBlob SHAを再確認する。
5. 作業開始時とSHAが異なる場合は最新正本を再取得し、他の変更を保持して差分を再適用する。
6. GitHubへ更新する。
7. 更新後のBlobを再取得し、JSON構文・件数・ID・順序・意図した差分を確認する。
8. 実際にGitHub上の反映を確認してから完了と報告する。

## 13. 検証と完了条件

変更内容に応じて、利用可能な既存スクリプト・テスト・GitHub Actionsを確認して実行する。存在しないスクリプト名や未実施のテストを実施済みと報告しない。

最低限、該当する範囲で次を確認する。

- JSONとして正常に読み込める。
- タグ件数・ID・英文タグ・配列順に意図しない変化がない。
- 重複・欠落がない。
- メタデータ・レビュー根拠・候補索引が維持・同期されている。
- 翻訳・分類・表現レベルの確認状態が独立している。
- 未判定とレベル0が区別されている。
- 分類先が現行taxonomyに存在する。
- 対象外のタグ・ファイルに意図しない変更がない。
- CSVインポートを行った場合はGitHub Actionsが成功している。
- UIを変更した場合は、コード検査・自動テストと実ブラウザ確認を区別して報告する。

完了報告には、取得元・対象範囲・変更ファイル・変更件数・変更前後の状態・実施した検証・未解決事項・コミットまたはActionsの状態を含める。

## 14. ドキュメント管理

- 現行のデータ整備・運用ルールは本書だけを正式な規範文書とする。
- READMEは概要と本書への案内を担当し、詳細な運用ルールを重複掲載しない。
